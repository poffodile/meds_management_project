### Roadmap — Medication Stock page (added 2026-07-13)

Owner chose to build **#30–#36 (items 2–8)** in order. **CD register (item 1)** is *not* here — it already exists as its own page (`/frontend2/controlled-drugs`) and the Stock page now **links to it** via a "CD register" button.

- 🔧 **#30** (v1 built 2026-07-13) — **Batch / lot tracking with per-batch expiry (FEFO).** **Built:** new `medication_stock_batches` table + `MedicationStockBatch` model (migration run locally); receiving stock (a `received` adjustment) now **creates a batch** with its own qty / expiry / lot no. / supplier; the med detail panel shows the **batch list, earliest-expiry-first, with a "Use next" badge** on the FEFO head; controller payload includes `batches` per med (guarded by `Schema::hasTable` so the page is safe before migrating). **Done in v2 (2026-07-13):** **FEFO auto-consumption** — `MedicationStockTransaction::apply()` now calls `consumeBatchesFefo()` on every consuming movement (administered / disposed / returned), drawing down the **earliest-expiry batches first**; a depleted batch is flagged `is_depleted` and drops off the list. Additive + safe (no-op when the table is absent or the sheet has no batches), so the rest of the app (med round etc.) is unaffected. **Still TODO (v3):** (1) Roll **expiry/low status up from batches** instead of the single `mar_sheets.expiry_date` (so the status pills reflect batch-level expiry). (2) **Backfill** batches for existing stock (meds received before this feature have none). (3) A `correction` recount doesn't rebalance batches — decide how a manual recount reconciles against batch quantities. — *Area: data model + Stock overview + Adjust form + `apply()`.*
- 🔧 **#31** (built 2026-07-13) — **Stock count / reconciliation mode.** **Built:** a new **"Stock count"** sub-tab where you enter the **physically-counted** quantity per item; the system computes **expected vs counted**, flags the **difference** (green Match / red shortfall / amber surplus), and lets you add a **reason** per discrepancy and a **witness (required for controlled drugs)**. **Post corrections** applies them in bulk via `POST /frontend2/stock-2/count` → each changed item posts a `correction` transaction (absolute recount) with the was/counted noted; CD rows without a witness are skipped server-side. ### Roadmap — bigger features (added 2026-06-30)

- 🔲 **#17** — **Medications dictionary / formulary.** Build a proper meds reference so the app stops parsing free-text `dose`/`dosage` and auto-fills **form, strength, unit, route, default dose, CD schedule**. Foundation for #15. **Agreed direction (2026-06-30):**
  - **Provider-agnostic med model** — our own normalised `medication` model + a pluggable "drug-data provider" interface, so the source (dm+d / FDB / RxNorm…) can change without touching the app.
  - **UK base = dm+d** (NHS Dictionary of Medicines and Devices) — free, NHS-standard, and the **same codes GP Connect (#18) uses** → store the dm+d/SNOMED code on each `mar_sheet`.
  - **Clinical engine = FDB (First Databank)** or a peer (Medi-Span / Multum / Micromedex / Vidal) for the things dm+d doesn't have — allergy cross-reactivity + interactions (#23). FDB Multilex maps to dm+d.
  - **Worldwide architecture, UK-first rollout** — design for many markets (add providers per country: dm+d UK, RxNorm US…), but ship UK first. NB other markets need their own regulators/integrations (CQC & GP Connect are UK-only).
  - **dm+d source:** prefer the **FDB feed** (they keep it current, so we may never touch TRUD); otherwise a **free NHS TRUD account** (registration is quick; dm+d is Open Government Licence). **Never** use unofficial GitHub mirrors for a clinical system.
  — *Area: data model + drug-data provider + medication forms everywhere.*
- 🔲 **#23** — **Allergy & drug-interaction checking.** Flag when a prescribed/administered med clashes with a resident's allergies (and, later, with their other meds). **v1 = allergy checking** — match the product's **ingredients** (from dm+d) against the resident's **coded allergies** (entered manually now, fed by **GP Connect** once live), plus a curated **allergen-class map** (penicillins, NSAIDs, sulfonamides…) for common cross-reactivity. **Later = full drug–drug interactions** via the **FDB** clinical engine (licensed). Must be framed as **decision-support, not a substitute for clinical judgement**, with clinical sign-off. — *Area: prescribing + Medication Round (prescribe-time + administer-time checks).*
- 🔲 **#18** — **GP Connect integration.** Connect to **NHS GP Connect** to pull/sync each resident's GP **medication record, allergies and key clinical info**, so prescriptions and changes flow from the GP rather than being typed in by hand. Medications/allergies come back **coded in dm+d/SNOMED** — which is exactly why #17 builds on dm+d and why coded allergies make #23 reliable. UK-only. — *Area: integrations + prescriptions.*
- 🔲 **#19** — **Reports page (CQC-aligned).** A reporting area producing reports mapped to **CQC** expectations — MAR compliance, missed/refused doses, controlled-drug audit, stock & expiry, etc. — viewable and **exportable for inspections**. — *Area: new Reports section.*
- 🔲 **#20** — **Incident reporting.** A page to **raise, categorise and review incident reports** (falls, medication errors, safeguarding, behaviour…), each with status/follow-up, who-what-when, and a link to the resident. Shows the list of incidents and their detail. — *Area: new Incidents section.*
- 🔲 **#21** — **Trend / pattern alerts.** Watch the data for **recurring patterns** and flag them — e.g. a resident is repeatedly **asleep when a particular med is due** (so it keeps getting omitted), recurring refusals, time-of-day patterns. Surface a "**noticed a trend**" alert so staff/clinicians can act (e.g. review the dose timing with the GP). — *Area: analytics + alerts.*
- 🔲 **#22** — **Book-out (leave of absence) for meds.** When a resident **books out / goes on leave** and takes their medication with them, mark those meds as **"booked out"** — responsibility passes to the resident/family for that period, so the doses **aren't flagged as missed** and the MAR reflects the absence. **Book back in** on return. — *Area: Medication Round / MAR + resident leave.*

- 🔲 **#27** (noticed 2026-07-09) — **Clinical-grade audit integrity for dose-review records (Missed doses "Undo").** Today Undo **hard-deletes** the `medication_dose_reviews` row. A change-log row (`medication_dose_review_logs`, append-only *in code*) snapshots what/who/when, but the original record is gone and the removal isn't shown on-screen once the dose flips back to outstanding. Owner chose to harden this to a **"Strong"** standard before go-live:
  - **Never hard-delete** — Undo **voids** the review (`status` → `voided`, keep the row) and stamps `voided_at` / `voided_by_user_id` / `void_reason`. Re-resolving revives the row; every transition stays logged.
  - **Require a reason** to undo (server-validated).
  - **Restrict undo to managers** — **decided 2026-07-09: `user_type` M/O/A only** (carers **N** and **CM** cannot).
  - **Surface it on screen** — a dose that was resolved-then-undone shows *"Previously resolved, then undone by X · reason"* + its change log inline, not just in the audit CSV.
  - **Immutable audit log** *(GO-LIVE — deferred 2026-07-09)* — the app is already append-only; add **DB-level triggers** that block `UPDATE`/`DELETE` on `medication_dose_review_logs`, so even a database user can't quietly erase history.
  - **Record privileged / direct-database access** *(GO-LIVE — deferred 2026-07-09)* — even legitimate DB-level access or emergency fixes (made outside the app) must **themselves be recorded** via database audit logging, so any change leaves a trace no matter how it was made. *(Owner: "the database should have something that can access and change things, but there should be a record if that happens.")*
  - **Decisions (2026-07-09):** manager set = **M/O/A only**; the two **DB-level** items above are **deferred to the go-live checklist** (do the app-level 1–4 now, DB-level 5–6 at launch — see also #26).
  - **Reuse:** the same pattern should later cover **Controlled drugs** and the **MAR** — this isn't Missed-doses-only. — *Area: data model + audit/compliance.*
